# 未读会话预分配目标 20 与余量调拨

## 已确认需求

- 仅客服01、客服02、客服03、李惠四个现有配置账号参与，目标由每人100改为20个未读客户会话。一个客户的多封邮件仍占一个名额。
- 先使用未归属的未读会话，按最早未读来信时间从旧到新分配，优先补给未读队列较短的账号。
- 未归属的可用会话不足时，允许从另外三个账号调拨；只从超过20个的账号调取，并至少给原账号留20个。
- 调拨候选按最早未读来信时间从新到旧选择；相同时间使用客户ID稳定排序。
- 总量不足时，在保留原账号20个和邮箱权限的约束下尽量均衡，不从不足或等于20个的账号继续抽取。例如0/10/10/19且无未归属会话时保持不变，避免反复调拨。
- 正被原客服打开的会话若发生调拨，弹窗提示归属变化，要求刷新会话，并保留原客服草稿。

## 方案比较与选择

采用用户选择的“保留20个、仅调拨余量”方案。另一方案是无论原账号剩余多少，都向当前不足20个的账号转移；后者会造成会话往返调拨，且不符合用户明确选择。

沿用现有30秒后台补齐任务及SQLite事务，不引入独立队列或WebSocket服务。页面增加只查询当前会话归属的轻量轮询；不重复查询邮件正文和外部订单服务。实现选择由开发者确定。

## 后端设计

1. 保留现有活动账号和邮箱权限校验，不调拨四人名单之外的会话。
2. 一轮先分配未归属会话，再从四人中有余量的账号向有权限的不足账号调拨。接收者始终优先选择当前未读数最少者；每次调拨更新双方计数。
3. 排除发送中和发送结果未知的会话；已读会话不参与。打开邮件自动已读的现有逻辑保留。
4. 分配和调拨在同一事务内执行，以原负责人和revision共同校验更新，审计同时保存原负责人、新负责人、目标、排序时间和本轮ID。失败整体回滚。
5. 轻量归属查询接口复用身份和邮箱权限验证，只返回当前会话的归属信息和识别调拨所需的版本，不访问外部订单数据库。
6. 页面提交发送时携带归属快照，服务端在登记发送前核对，阻止旧页面在被调拨后继续发送。不是一般work revision冲突：草稿和处理状态变更不应误触发。

## 页面设计

- 仅在打开了会话且页面可见时轮询；切换会话后旧请求结果失效，回到页面时立即检查。
- 检测到该会话从原客服转走后，只提示一次：该会话已分配给其他客服，请刷新后继续处理。
- 提示出现后禁止以旧归属继续发送，避免轮询与发送之间的时间差。服务端同时做最终校验。
- 刷新当前会话和列表，不强制浏览器整页刷新；原客服文字草稿及已选附件保留，不能静默清空或将原客服草稿转交新客服。
- 普通编辑或草稿保存导致revision变化，不弹归属变化提示。

## 验证

- 未归属先分配且旧邮件优先；调拨新邮件优先；供给账号保留20；不足时优先补最低队列。
- 多轮执行幂等，无往返调拨；四人之外、无权限、停用账号、已读、发送中、结果未知不调拨。
- 多封邮件同客户只占一个名额；归属更新和审计原子提交，失败回滚。
- 两浏览器模拟：原客服打开会话后被调拨，提示一次、保留草稿，旧页面发送被拒绝；切换会话后的旧轮询不能误提示新会话。
- 部署前核对四个线上账号配置，目标改20必须与具备调拨保护的代码配套。当前阶段只准备实现，尚未修改线上目标或任何会话归属。

## 范围

不改未读定义、邮件正文、订单加载和竞品扫描项目。不会为了强制每人恰好20个而把所有历史已归属会话重新洗牌；多余会话只在其他账号有缺口时调拨。
